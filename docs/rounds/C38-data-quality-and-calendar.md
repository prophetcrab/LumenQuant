# 迭代记录 C38：数据页与日历——真实数据反向校验

## 动机

C37 横扫策略时顺手点开数据页，发现标的下拉里每只股票出现两次。
顺着这条线查下去，牵出三个缺陷和一次**真实数据反向校验日历**的机会。

## 缺陷一：数据页标的下拉重复

覆盖表的每一行是 `(symbol, timeframe)`，前端直接 `map` 成 `<option>`，
于是每只有两个周期的标的都会被列出两次（14 个标的 → 28 个选项）。

改为按 symbol 去重。

## 缺陷二：导入周期硬编码 15m，A 股真实日线 CSV 无法导入

```ts
form.set("timeframe", "15m");   // 永远
```

而后端明确支持 A 股的 `1d`（真实交易所导出的就是日线）。也就是说：
用户拿到一份真实日线 CSV，在界面上无法导入——只能直接调 API。

修法：按标的市场给出允许的周期（加密 = 基础周期；A 股 = 基础周期 + `1d`），
并让"数据质量"面板跟随所选周期，可以查看日线而非只看得见 15m。

## 缺陷三：缺口统计把周末和午休当成数据损坏

真实 A 股日线 158 根，质量面板报 **341 个缺口**。算法是：

```python
if delta > step:
    gaps += delta // step - 1
```

日线步长是 1 天，但交易日之间隔着周末和节假日。341 这个数字完全来自
"两个交易日相隔 3 天"这类正常间隔，把一份干净数据描述成灾难性损坏。

修法：按市场日历计算期望值。

- **日线**：`expected = 区间内交易日数`，缺口 = `expected - 实际根数`
- **分钟线**：每个交易日应有 `(收市 - 开市) / step` 根，逐日比对
- 首尾两天不算：抓取窗口可能从盘中开始，而"今天"还没收盘——
  把这两天算进去会报出根本不存在的缺失

## 真实数据反向校验：2026 春节少休了一天

修完缺口算法后日线仍报 1 个缺口：`2026-02-23`。查真实数据：

```
2026-02-13 Fri bar
2026-02-14 Sat —
2026-02-15 Sun —
2026-02-16 Mon —   ← 我们标为「休市」✓
...
2026-02-20 Fri —   ← ✓
2026-02-21 Sat —   ← ✓
2026-02-22 Sun —
2026-02-23 Mon —   ← 我们标为「交易日」✗
2026-02-24 Tue bar
```

**2026 年春节实际休到 2 月 23 日（含），2 月 24 日恢复交易。**
我们临时的节假日表只写到 2 月 21 日，把 2 月 23 日（周一）算成了交易日。

这是用真实行情反过来检验日历——比人工核对官方公告更可靠，
因为数据本身就是交易所的最终答案。

修完后，用 301 根真实日线覆盖 2025-07 至 2026-10，逐日比对：

```
calendar says trading but no bar: []
calendar says closed but bar exists: []
```

一年多区间内日历与真实数据**完全一致**。

## 缺陷四：导入后质量面板显示旧数据

`/api/data/quality` 与 `/api/data/coverage` 有 30 秒缓存。
CSV 导入成功后缓存不失效，用户看到的还是导入前的数字——
"我明明导入了，怎么还是原来的根数？"

修法：给 `TTLCache` 加 `invalidate(prefix)`，导入成功后精确清掉
`coverage` 与 `quality:{symbol}:` 相关的键。

## 设计取舍

- **为什么不在缺口里区分"数据缺失"和"市场休市"**：修完后已经没有后一种情况——
  日历覆盖的年份里，休市日不会产生期望值。未覆盖年份仍会误判，
  但那是日历维护问题，已由 `calendar_coverage()` 显式告警（见 C33）。
- **为什么首尾两天不计缺口**：任何一次抓取都可能是部分区间。
  严格要求首尾完整会让每一次正常同步都报缺口，告警很快就会被无视。
- **为什么用真实数据校验日历**：节假日表是人工维护的，一定会有错。
  真实行情是免费、权威、可持续的对照物。这个检查值得固化成脚本。
