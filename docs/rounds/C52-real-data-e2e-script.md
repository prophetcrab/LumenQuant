# 迭代记录 C52：真实数据端到端验收脚本

## 动机

C24–C51 修了几十个缺陷，每次都用了真实数据或真实浏览器验证——
但这些验证是**一次性的**：写一段临时脚本，看一眼输出，删掉。
下一轮改动可能破坏其中任何一环，而没人会重新手写一遍验证。

这一轮把这条链路固化成脚本。

## 脚本做什么

`tests/stress/real_data_e2e.py` 在一个临时数据库上跑完整链路：

| # | 步骤 | 断言 |
|---|---|---|
| 1 | 同步真实数据 | `ok=true`，日线 > 200 根 |
| 2 | 日线质量 | 缺口 0、非法 OHLC 0、重复时间戳 0 |
| 3 | 创建 A 股账户 | 币种 CNY |
| 4 | 真实数据回测 | 有成交且 `currency == "CNY"` |
| 5 | 真实价下单 + T+1 | 成交价为正、`available=0`、当日卖出 409 |
| 6 | 自动实例执行 | tick 返回 `executed`/`no_new_bar`/`insufficient_data` |
| 7 | 风控保护可见 | 实例 `protected=true` 且无告警 |
| 8 | 权益恒等式 | `cash + 持仓市值 == equity`，误差 < 0.01 |
| 9 | 助手市场隔离 | 回答中无 `USDT` |
| 10 | 归档停止实例 | 归档后所有实例 `running=false` |

退出码非 0 表示某一步失败。

## 为什么这比单元测试更有价值

单元测试断言的是函数的契约，这个脚本断言的是**用户看到的结果**。
第 8 步的权益恒等式、第 5 步的 T+1 拦截、第 10 步的归档——它们横跨
四五个模块，任何一处改动导致的不一致都会在这里暴露，而在单个模块的
测试里可能完全正常。

它也正是 C39（实盘自动运行绕过确认头）、C43（归档后实例仍在交易）
这类缺陷的检测器：这两个问题都不是某个函数的错，而是模块之间的缝隙。

## 设计取舍

- **为什么用临时数据库**：每次运行都从零开始，不受既有数据影响，
  也不会污染开发库。代价是每次都要重新同步（约 3 秒），可以接受。
- **为什么不用 pytest 包装**：它需要外网。放进 `tests/` 会让
  `pytest -q` 在离线环境下失败。放在 `tests/stress/` 并按脚本运行，
  与 `verify_calendar.py` 的处理方式一致。
- **为什么断言 tick 的三种结果都算通过**：不同时刻运行会落到不同分支
  （新 K 线 / 无新 K 线 / 数据不足），这里验证的是"实例能被调度且不报错"，
  不是某个特定分支。
- **为什么第 9 步只断言"无 USDT"**：具体标的会随账户与数据变化，
  但"不跨市场"是稳定不变的约束。
