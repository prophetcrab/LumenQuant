# 迭代记录 C60：同一标的上的多个实例

## 动机

自动运行页允许用户对同一标的创建多个实例——不同的策略、不同的参数。
这在研究上是合理的（比较几套逻辑在同一标的上的表现），但执行层的行为
值得验证。

## 验证：仓位不会叠加

100k 账户，对 BTCUSDT 创建 3 个 `position_pct=0.5` 的实例，各跑 3 轮：

```
instance 0: 201
instance 1: 201
instance 2: 201
positions: [('BTCUSDT', 49984.41)]
equity=99935.01 exposure=50.0% cash=49950.59
```

持仓只有 1 笔，敞口 50%——**没有叠加成 150%**。原因是执行层在开仓前检查
`position <= 0`：第一个实例建仓后，其余实例看到已有持仓就不再买入。

这个保护是正确的，也是必要的。

## 缺陷：静默空转

但第二个实例的日志是：

```
('signal', 'buy · 基准建仓')
```

每一根新 K 线都记一条"产生买入信号"，然后什么也没发生。用户看到这条日志，
合理的理解是"策略在尝试建仓"，而实际上它永远不会成功——
除非第一个实例平仓。

更糟的是风险页：两个实例都"运行中"、都"无止损保护"，
但没有任何地方提示"这两个实例抢同一个仓位"。

### 修法

1. **执行层记录原因**：

   ```python
   elif signal.action == "buy" and position > 0:
       self._log(row.id, "warn", "position_already_open",
                 f"已有 {row.symbol} 持仓，跳过买入（同一标的的多个实例不会叠加仓位）")
   ```

   `warn` 级别会走 C34 的去重窗口，不会每 6 秒刷一条。

2. **风险页集中告警**：

   ```
   BTCUSDT：买入持有、买入持有 同时运行，只有最先开仓的实例会实际持仓
   ```

   按标的聚合运行中的实例，数量 > 1 就生成一条。

## 设计取舍

- **为什么不去禁止同标的的多实例**：研究场景下"同一标的跑五套逻辑"是
  合理需求。禁止会砍掉一个真实用途，而问题只在于信息不透明。
- **为什么不改成"每个实例各管一份仓位"**：那需要按实例拆分持仓
  （`(account, symbol, instance)` 三元组），是订单与持仓模型的大改。
  当前设计是"一个账户一个标的只有一个持仓"，简单且与真实券商一致
  （同一账户同一标的确实只有一个持仓）。
- **为什么告警放在风险页而不是自动运行页**：风险页的职责就是集中展示
  需要用户注意的状态。自动运行页展示的是每个实例的细节，
  重复实例是**跨实例**的问题。
- **为什么用 `warn` 而不是 `info`**：这不是正常流程的一部分。
  用户看到黄色标记才会去想"为什么"。

## 验证

| 检查项 | 结果 |

| 第二个实例记录 `position_already_open` | ✅ 新增测试 |
| 风险页告警点名冲突的标的与策略 | ✅ 新增测试 |

## 后续

- 若要支持"每个实例独立仓位"，需要在 `Position` 上加实例维度，
  并改动撮合、风控与账本。这是一个结构性变更，需要单独立项。
- 更轻量的替代方案：在创建实例时若同标的已有运行实例，
  返回一个确认提示（"该标的已有实例在运行，新实例不会叠加仓位"）。
  这属于 UI 层防呆，与后端告警互补。
