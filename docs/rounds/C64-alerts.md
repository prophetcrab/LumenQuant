# 迭代记录 C64：告警中心

## 动机

系统里最需要人立刻知道的三件事，此前只写日志：

1. **风控熔断触发**——所有新开仓被禁止，直到人工重置
2. **保护性离场**——止损/止盈平了仓，或平仓失败（持仓失去保护）
3. **下单失败**——网关不可用、资金不足、被风控拒绝

这些事件散落在 `runtime_logs`（按实例、200 行环形缓冲）和 `audit_logs`
（只增不改、面向取证）里。前者会被后续日志冲掉，后者没有"我是否已处理"的概念。

用户想知道的是"有没有需要我看一眼的事"，这需要一个新的数据形状。

## 实现

### 与审计日志的区别

|  | audit_logs | alerts |
|---|---|---|
| 目的 | 取证：发生过什么 | 决策：需要我做什么 |
| 数量 | 全量 | 只记需要人注意的 |
| 可确认 | 否 | 是（acknowledged） |
| 级别 | 无 | info / warning / critical |
| 归类 | action 字符串 | category（熔断、止损、网关…） |

### 去重

同一个 `(account_id, category, ref_id)` 的未确认告警在 5 分钟内只写一条。
调度器每 6 秒一轮，不去重会在一个熔断场景下每分钟产生 10 条相同记录。

### 接入点

| 事件 | 级别 | category |
|---|---|---|
| 熔断触发 | critical | `breaker` |
| 止损/移动止损/止盈离场 | critical | `stop_loss` / `trailing_stop` / `take_profit` |
| 保护性离场失败 | critical | `exit_failed` |
| 自动下单被业务规则拒绝 | warning | `order_rejected` |
| 下单网关调用失败 | critical | `gateway_failure` |

### 接口

```
GET  /api/alerts?account_id=&unacknowledged_only=&level=&limit=
GET  /api/alerts/summary?account_id=
POST /api/alerts/{id}/ack
POST /api/alerts/ack-all?account_id=
```

### 前端

新增「告警」页（侧栏在「风控」之后）：

- 四张统计卡：待确认 / 严重 / 警告 / 提示
- 待确认 / 全部 切换
- 列表：时间、级别徽章、类型（中文）、标题与详情、确认按钮
- 已确认的行降低透明度，一眼区分

## 实测

触发一次熔断（把权益从 100 万观察到 90 万）：

```
{"unacknowledged": 1, "by_level": {"critical": 1, "warning": 0, "info": 0}}
```

页面上显示：

```
待确认 1   严重 1   警告 0   提示 0

10/21 14:16:45  严重  风控熔断  风控熔断已触发，新开仓被禁止
                              daily loss limit hit (-9.92% <= -5.00%)   确认
```

连续观察 4 次只产生 1 条（去重生效）。

## 一个真实的边界：A 股当日止损

测试里发现：A 股实例当日买入后触发止损，`close_position` 被 T+1 拒绝，
于是产生的是 `exit_failed` 而不是 `stop_loss`。

这个行为是正确的，而且信息更重要——**持仓还在，且没有保护**。
测试因此接受两者中的任意一个，但断言必须先有告警产生。

## 设计取舍

- **为什么 `raise_alert(commit=False)` 默认不提交**：告警常在更大的事务里
  产生（一次下单被拒），如果外层回滚，告警不该指向一个不存在的订单。
- **为什么确认是单向的**：确认表示"我已看到"。取消确认没有真实用途，
  而且会让人反复处理同一件事。
- **为什么不发邮件/Webhook**：那需要配置、重试与失败处理，
  是独立的集成工作。当前把告警做成可查询的状态，前端 10 秒轮询。
- **为什么不做全局未读数徽章**：需要每个页面都知道它，属于跨页面状态。
  当前进入告警页即可看到总数；后续可以在侧栏加角标。
- **为什么不把告警写进审计**：两套记录关注点不同。告警是工作队列，
  审计是历史档案。混在一起会让两者都变差。
