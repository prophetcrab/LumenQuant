# 迭代记录 C48：多账户场景下的两个盲点

## 动机

前几轮都在单账户视角下工作。实际使用中账户会不断累积——
当前的开发库里就有 9 个账户、两种货币（CNY 5 个、USDT 4 个）。
多账户场景暴露了两个问题。

## 缺陷一：账户切换器不显示市场

顶部下拉只显示名称与"模拟/实盘"：

```
最终验收A股 · 模拟
最终验收加密 · 模拟
```

而切换账户会让**整个页面**改变语义：货币符号、涨跌停规则、T+1、
可用标的列表、可交易的时间段——全部不同。两个账户如果名字起得相似，
用户切错了不会得到任何提示，只会在下单时遇到一个莫名其妙的错误。

修法：选项补上市场标签。

```
最终验收A股 · 模拟 · A股
最终验收加密 · 模拟 · 加密
```

## 缺陷二：没有跨账户合计，而且不能简单相加

账户页只有逐个卡片展示。用户想回答"我总共还有多少现金"，需要自己
把 9 个数字加起来——其中 5 个是人民币、4 个是美元。

**直接把两种货币相加是错的。** 系统里没有任何汇率数据，
任何"看起来合理"的换算都会给出一个用户无法核对的数字。

修法：账户列表顶部加一行按币种分组的合计：

```
合计   ¥3,279,264.76 · 5 个账户    $3,191,931.38 · 4 个账户
```

两个数字并列，各自带符号与账户数。用户一眼能看到全貌，
也知道它们不能相加。

## 设计取舍

- **为什么不做汇率换算**：汇率是外部事实，且随时变化。
  系统不持有汇率来源，硬编码一个会在几周内失真，接入外部 API 则引入
  新的失败点与合规问题。分组展示是唯一诚实的选择。
- **为什么合计用现金余额而非权益**：权益需要持仓市值，而持仓市值需要
  逐账户请求实时报价。账户页要看到 9 个账户的权益意味着 9 次行情查询，
  在打开页面时做这件事会让加载明显变慢。现金余额是账户记录本身的字段，
  一次列表请求就够。组合页仍提供单账户的完整权益。
- **为什么合计放在账户列表卡片内部而不是单独一张卡**：它是对"下面这些
  账户"的汇总，紧挨着列表才有意义。单独一张卡会让人以为它是另一个独立指标。

## 后续

- 如果将来接入汇率，合计可以给出一个"折算为本位币"的总数，
  但必须显示汇率来源与时间戳。
- 账户页的现金合计不包含持仓市值。若用户需要"总资产"，组合页的单账户
  视图更准确；跨账户总资产需要聚合接口，属于下一步。
