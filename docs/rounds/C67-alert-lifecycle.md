# 迭代记录 C67：告警的生命周期

## 动机

C64/C66 建的告警系统有两个未处理的问题：

1. **无限增长**：已确认的告警不会消失。一个每天触发几次熔断的系统，
   一年后表里有上千行，而其中真正有用的可能只有最近几天。
2. **无法按类型筛选**：出问题时最常见的问法是"最近的离场失败有哪些"，
   而界面只能按级别或是否确认过滤。

## 实现

### 保留策略

```python
def prune(self, *, keep_days=30, account_id=None) -> int:
    cutoff = utcnow() - timedelta(days=keep_days)
    delete(Alert).where(Alert.acknowledged.is_(True), Alert.created_at < cutoff)
```

**未确认的告警永不按时间删除**。这一点是刻意的：没人看过的告警仍然是一个
待回答的问题，不管它多老。删掉它等于假装问题解决了。

接入调度器，与运行日志修剪同一个小时级节拍：

```python
purged = AlertService(session).prune(keep_days=self.alert_retention_days)
```

保留天数通过 `LQ_ALERT_RETENTION_DAYS` 配置，默认 30 天。

### 类别过滤

- `GET /api/alerts?category=` 精确过滤
- `GET /api/alerts/categories` 返回各类型的数量，用于构建下拉

前端在告警卡片头部加一个下拉：

```
全部类型
风控熔断（1）
```

括号里是**该类型的总数**（含已确认），不是当前视图的条目数——
它描述的是"这个系统产生过多少这类事件"，不是"筛完后剩几条"。

## 实测

插入三条记录（60 天前已确认 / 60 天前未确认 / 刚已确认），
用 `keep_days=30` 修剪：

```
deleted: 1

剩余：
  ✓ 未处理的旧告警   ← 60 天前，但未确认，保留
  ✓ 新告警           ← 刚确认，未超过保留期
  ✗ 旧告警           ← 已删除
```

分类接口返回：

```json
[{"category": "breaker", "count": 1}]
```

页面上下拉显示"全部类型 / 风控熔断（1）"。

## 设计取舍

- **为什么按"确认"而不是"级别"决定去留**：`info` 级别的告警也可能很重要
  （比如"实例已启动"），`critical` 的也可能已经处理完了。
  状态比级别更能表达"这件事还需要我做什么"。
- **为什么保留期默认 30 天**：一个月的窗口足够回顾"上周那次熔断是什么原因"，
  又不至于留下太多。可通过环境变量调整。
- **为什么 `categories` 单独一个接口**：它需要 `GROUP BY`，
  与列表查询的索引路径完全不同。塞进列表响应会让每次翻页都多算一次聚合。
- **为什么下拉里的计数包含已确认**：类型分布是系统行为的画像，
  不是当前视图的统计。若只数未确认，用户切换筛选时数字会跳变，反而更困惑。
- **为什么 `prune` 也要接受 `account_id`**：手动清理某个账户的历史时有用，
  自动调度则传空表示全局。

## 后续

- 告警仍缺少"按时间范围查询"（如"上周的 critical"）。
- `categories` 的计数会随修剪变化——已删除的历史不再计入。
  如果需要长期趋势，应当另建聚合表，而不是靠保留明细。
