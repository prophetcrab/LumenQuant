# 迭代记录 C27：止损止盈自动运行缺失与统一

## 发现的缺陷（严重）

探测时发现一个一致性缺口：

| 能力 | 回测引擎 | 自动运行 |
|---|---|---|
| 止损 `stop_loss_pct` | ✅ 支持 | ❌ **完全没有** |
| 止盈 `take_profit_pct` | ✅ 支持 | ❌ **完全没有** |
| 移动止损 | ❌ 不支持 | ❌ 不支持 |

后果很直接：**同一个策略，回测里止损保护收益，实盘/模拟运行时却完全裸奔**。
用户按回测结果调好 5% 止损，开自动运行后发现亏损可以无限扩大。

这是比"某处算错"更危险的一类问题：两边都"能跑"，只是行为不一致。

## 实现

### 1. 共享止损模块 `app/modules/risk/stops.py`

纯函数，回测与运行器共用同一套判定，从根本上消除行为差异：

| 规则 | 触发 | 成交价 |
|---|---|---|
| 止损 | `bar_low <= entry × (1-pct)` | 跳空时取 `open`（更差），否则取止损价 |
| 移动止损 | `bar_low <= peak × (1-pct)`，且 `peak > entry` | 同上 |
| 止盈 | `bar_high >= entry × (1+pct)` | 跳空时取 `open`（更好），否则取目标价 |

优先级：止损 → 移动止损 → 止盈。同一根 K 线同时触及止损与止盈时按**止损**处理
（不给回测"假设吃到好成交"的偏差）。

### 2. 回测引擎改用共享实现

原实现内联在 `engine.py` 里，现替换为 `evaluate()` 调用，`BacktestConfig` 新增
`trailing_stop_pct`，`_OpenPosition` 记录 `peak_price`。

### 3. 运行器新增逐 tick 保护

`RuntimeService.protect_positions()`：

- 每个调度周期扫描运行中实例的持仓；
- 用实时价评估止损/止盈/移动止损；
- 触发即调用 `close_position` 平仓，写日志与 `peak_price`；
- 空仓时重置峰值，避免下次入场带着旧峰值。

放在调度器最前面执行——**即使策略评估抛异常，止损也必须先跑**。

## 修复过程中的两个语义缺陷

### 缺陷 1：移动止损自我触发

第一版用"当根高点"更新峰值再判断回落：

```
bar: open=100, high=120, low=100, entry=100, trail=10%
→ 峰值更新到 120，回落线 108，low=100 <= 108 → 立即触发
```

任何一根振幅大的 K 线都会误触发。

修复：用**上一根之前的峰值**判断（`peak_before`），当根高点只用于更新下一轮的峰值。
OHLC 无法提供根内先后顺序，这是唯一自洽的约定。

### 缺陷 2：价格获取失败被静默吞掉

`protect_positions` 里 `except Exception: continue` 会让行情源故障时
**保护静默失效**，持仓继续裸奔。

修复：写入 `last_error` 与 `price_unavailable` 日志，并在返回值里标记，
用户可以立刻看到"保护没生效"。

## 教训

**"两个地方实现同一件事"是缺陷温床。** 回测有止损、运行时没有，
不是因为谁写错了，而是因为它们各自实现。共享纯函数是最便宜的修复方式，
也让两者从此不可能漂移。

第二个教训：**`except Exception: continue` 在风控路径上是反模式**。
它把"无法保护"伪装成"无需保护"，而这两者后果天差地别。
