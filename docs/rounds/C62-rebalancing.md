# 迭代记录 C62：定期再平衡

## 动机

C61 的多标的回测里，每个 sleeve 拿到初始资金后各自复利到结束。这意味着：

- 涨得最猛的标的会在组合里占据越来越大的权重
- 组合风险逐渐向单一标的集中
- 与"我打算保持 1:1:1 配置"这个真实意图不符

真实组合管理会定期把权重拉回目标。这一轮加上它。

## 实现

新增 `rebalance_bars` 参数（0 表示不再平衡）：

```json
{ "symbols": [...], "weights": [1,1,1], "rebalance_bars": 20 }
```

### 算法

sleeve 是独立回测的产物，无法在引擎内部"转账"。所以改为在**收益流**层面
重建：

1. 把每条 sleeve 权益曲线转成逐根收益率
2. 从总资金按目标权重分配初值
3. 每根 K 线让各 sleeve 的份额乘上自己的收益率
4. 每到再平衡点，把总额按目标权重重新分配

```python
for index in range(1, len(common)):
    for slot in range(len(curves)):
        values[slot] *= returns[slot][index]
    if index % rebalance_bars == 0:
        total = sum(values)
        values = [total * share for share in shares]
```

这假设份额可任意分割（不考虑手数）。真正的"按手数再平衡"需要订单级模拟，
那是另一个引擎；这里是权重研究，不是执行模型——产出的 `rebalance_bars`
与 `rebalance_count` 让读者知道用了哪种假设。

## 实测（BTC/ETH/SOL 等权，300 根 1h）

| 再平衡周期 | 收益 | 最大回撤 | Sharpe | 次数 |
|---|---|---|---|---|
| 不再平衡 | **+31.20%** | **2.77%** | 19.23 | 0 |
| 每 20 根 | +26.57% | 2.08% | 18.98 | 11 |
| 每 50 根 | +26.62% | 2.26% | 18.81 | 4 |

这正是再平衡的经典权衡：

- **收益下降**（31.2% → 26.6%）：因为不断削减赢家、补仓输家
- **回撤下降**（2.77% → 2.08%）：因为风险不再向单一标的集中
- **频率越低越接近不再平衡**（每 50 根 26.62% vs 每 20 根 26.57%，
  差异已经很小）

数字本身说明机制在正确工作，而不是写了个空壳。

## 设计取舍

- **为什么在收益流上重建而不是改引擎**：引擎处理"一个标的的资金曲线"，
  再平衡是"多个标的之间的资金调度"。把后者塞进前者会让引擎承担它不该有的
  职责，也会让单标的回测路径变复杂。
- **为什么允许任意 bar 周期而不是"每日/每周/每月"**：用户回测的 timeframe
  不固定（1h、1d 都有），按 bar 数最直接。前端提示"每 N 根 K 线"。
- **为什么再平衡不产生交易记录**：它只调整 sleeve 之间的份额，
  不改变 sleeve 内部的持仓。把再平衡算成交易会让"交易总数"失去意义
  （它应该只反映策略信号）。
- **为什么逐标的收益不受再平衡影响**：`components[].return_pct` 描述的是
  "该策略在该标的上"的表现，与组合如何调配资金无关。已加测试锁定这一点。

## 后续

- 再平衡不考虑手续费。每次再平衡的真实成本取决于调仓幅度与手数，
  在低换手策略上影响很小，但值得在文档里标注（已在算法的取舍说明里）。
- 可以增加"容差带再平衡"（偏离目标超过 X% 才调整），这比固定周期更贴近实务，
  减少无谓调仓。
