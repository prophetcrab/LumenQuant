# R15 可观测性

## 需求设计
回答三个运维问题：请求是否失败、哪里慢、谁改了什么。要求零外部依赖（单机部署），
并且能直接在 UI 中查看。验收：每个响应带 `X-Request-ID`；`/api/system/metrics` 返回请求量、
错误率、状态码分布、最慢路由、缓存命中率、后台引擎状态；审计可按动作过滤并汇总。

## 代码编写
- `core/observability.py`：`RequestContextMiddleware`（请求 ID、耗时、状态码、异常日志）+ `Metrics`（按路由聚合）。
- `modules/system/router.py`：`/metrics`、`/audit`、`/audit/summary`。
- 前端 `SystemPage`：运行时长、请求量、5xx、缓存命中、最慢接口、引擎状态、审计流水与动作统计。
- 导航新增“系统”。

## 代码审查
1. 健康检查与指标端点自身不写访问日志，避免自我放大噪声（已处理）。
2. 中间件异常路径也必须计数，否则 5xx 会被漏记（已处理）。
3. 契约：中间件加在 CORS 之前注册，保证 CORS 头仍能附加到响应（Starlette 逆序执行，已实测响应正常）。
4. 指标为进程内统计，重启清零；文档中明确这不是持久化时序库（限制说明）。

## 优化
- 路由聚合用 `method + path`，避免把路径参数拆成无限 key。
- 前端 5 秒刷新指标、15 秒刷新审计，降低自身开销。

## 测试
集成 3 例：请求 ID 透传、指标累计与 404 计数、审计写入与汇总。全量 `pytest`：103 passed。
浏览器实测：4 个引擎均为“运行中”，审计日志显示账户创建、入金、下单、策略实例创建。

## 压力测试
指标写入为内存字典，无锁竞争热点；R19 与整体压测一并复测。

## 报告
可观测性闭环。下一轮做数据管理与导入导出。
