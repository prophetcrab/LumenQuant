# 迭代记录 C93：批量加入候选标的

## 动机

C92 让「加入」变成「加入并导入历史」。但筛选页一次展示 50 只候选，逐只点击
意味着 50 次请求、约两分钟等待（每只同步 1–2 秒），而用户通常只想挑其中几只。

## 实现

`POST /api/screener/add-symbols`：

```json
{"codes": ["600000.SH", "600015.SH", "600016.SH"], "sync": true}
```

一次同步调用覆盖整批，返回：

```json
{"requested": 5, "created": 3, "already_present": 1, "synced": 4,
 "failed": [{"code": "BADCODE", "reason": "缺少交易所后缀"}],
 "daily_bars": 3200, "intraday_bars": 1280,
 "detail": "新增 3 只、同步 4 只（3200 根日线、1280 根 15 分钟线），1 只失败"}
```

### 四个细节

1. **去重**：同一批里重复的代码只处理一次，且 `requested` 保留原始条数，
   让"提交了 4 个、实际 3 个"这件事可见。
2. **区分新增与已存在**：`created` 与 `already_present` 分开计数。只报"处理了
   N 只"会让用户不知道哪些真正进来了。
3. **单个坏代码不拖垮整批**：格式不合法的进 `failed`，其余照常处理。
   批量操作里"有一个错就全不做"通常不是用户想要的。
4. **部分失败仍返回 201**：这是部分成功，不是失败的请求。具体哪些失败在
   `failed` 里说明。

### 前端

候选表加勾选列与全选，卡片右上角出现「批量加入并导入 N」。
按钮文案从旧的「加入标的」改成「加入并可回测」，因为现在的行为确实如此。

## 验证

真实腾讯数据，5 只代码（含 1 个已存在、1 个格式错误）：

```
5.3s  201
{'requested': 5, 'created': 3, 'already_present': 1, 'synced': 4,
 'failed': [{'code': 'BADCODE', 'reason': '缺少交易所后缀'}],
 'daily_bars': 3200, 'intraday_bars': 1280}
```

单只约 1.5 秒，批量 5 只 5.3 秒 → 摊到每只 0.6 秒（HTTP 连接复用与
并发同步的收益）。

3 项集成测试：整批登记、坏代码不拖垮整批、已存在单独计数。

2K 浏览器：勾选 3 行后按钮显示「批量加入并导入 3」。

## 回归

- 后端 **522 passed**（新增 3 项）
- 前端 66 passed，`tsc` 干净，构建通过

## 已知限制

1. **上限 50 只/批**：与单页展示数量一致；更多应走 `/api/cn/data/sync`。
2. **同步仍是串行的**：`CnDataSyncService` 逐只拉取。50 只约 75 秒，
   前端在此期间显示「导入中…」。真正的并发同步需要改动 sync 服务，
   本轮未做。
3. **部分失败不回滚**：已成功的标的保留，失败的列在 `failed` 里，
   用户可重试。
