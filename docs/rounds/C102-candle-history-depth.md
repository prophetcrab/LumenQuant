# C102：K 线历史深度（回测可用数据量）

## 问题

回测层的契约是 `bars <= 20_000`，但数据层有三处独立的上限，每一处都会**静默**
返回比请求更少的数据。结果是一个需要两年数据的策略，实际只拿到几天到几个月。

修复前的实测数据量：

| 标的 | 周期 | 根数 | 跨度 |
|---|---|---|---|
| BTCUSDT | 15m | 1,002 | 10 天 |
| BTCUSDT | 1d | 1,000 | 2.7 年 |
| 600519.SH | 15m | 320 | 35 天 |
| 600519.SH | 1d | 800 | 3.3 年 |

A 股 15m 只有 35 天——任何需要几百根暖机的策略，或任何跨月分析，都做不了。

## 三处截断

### 1. `MarketService.candles` 硬上限 5,000

```python
limit = max(1, min(int(limit), 5000))
```

回测请求 20,000 根，实际拿到 4,999 根，**没有任何提示**。

### 2. 路由层 `Query(le=5000)`

即使服务层放开，`GET /api/market/candles?limit=20000` 也会被 FastAPI 直接
422 拒绝。这是第二道独立的闸门。

### 3. `BinancePublicSource.klines` 单次 1,000 根且不分页

```python
{"limit": max(1, min(limit, 1000))}
```

Binance 单次上限就是 1,000，原实现把请求夹到 1,000 后返回——请求 8,000 根
只得到最近 1,000 根。**这是加密 15m 只有 10 天的直接原因。**

### 4. `TencentSource` 的上限与请求方向相反

```python
limit=max(1, min(limit, 1000))
```

但腾讯 m15 的真实上限是 **800**，且**超过 800 会退化为 320**。实测：

```
n=800 -> 800 根
n=900 -> 320 根   ← 请求更大，得到更少
```

请求 2,000 根会得到 320 根，比请求 800 还少。

## 上游真实能力（2026-10 实测）

| 源 | 周期 | 上限 | 说明 |
|---|---|---|---|
| Binance 公共 | 任意 | 无实际上限 | 单次 1,000，用 `startTime`/`endTime` 分页，历史可回溯 2017 |
| 腾讯 | 15m | **800** 根 | 超 800 退化到 320；约 50 个交易日 |
| 腾讯 | 60m | **500** 根 | 超 500 退化到 320 |
| 腾讯 | 1d | **2,000** 根 | 超 2,000 返回结构异常；约 8 年 |
| 新浪 | 15m | 500 根 | 超 500 返回 `null` |
| 东方财富 | 15m | 496 根 | 本机 IP 已被封禁，不可用 |

**A 股分钟线受免费源硬限制**，无法通过换源突破。要更长的小时级历史只能：
付费数据源、自行落地日线后按需聚合、或导入 CSV。

## 修复

### 分页（Binance）

`klines` 现在支持双向分页，对应两种调用意图：

```python
# 不传 start_ms：「最近 N 根」——往回翻，用 endTime
bars = source.klines("BTCUSDT", interval="15m", limit=8000)

# 传 start_ms：「从某点往后 N 根」——往前翻，用 startTime
bars = source.klines("BTCUSDT", interval="1h", limit=70000, start_ms=...)
```

两个方向各用自己的游标，混用会重复取同一页并产生重复时间戳。实测验证：

```
请求  1000 ->  1000 根  | 异常间隔=0 重复=0
请求  3000 ->  3000 根  | 异常间隔=0 重复=0
请求  8000 ->  8000 根  | 异常间隔=0 重复=0
```

### 精确上限（腾讯）

把实测上限写成常量，避免"请求更大、得到更少"：

```python
MAX_INTRADAY_BARS = 800
MAX_DAILY_BARS = 2000
```

### 1h 原生导入

之前小时线靠 800 根 15m 聚合，只有 300 根。现在从 `interval="1h"` 单独导入，
可回溯到 2017——这是加密长期研究最实用的周期。

### 深度可配置

```env
LQ_CRYPTO_SYNC_INTRADAY_LIMIT=8000    # 15m，约 83 天
LQ_CRYPTO_SYNC_DAILY_LIMIT=2000       # 1d，约 5.5 年
LQ_CRYPTO_SYNC_HOURLY_LIMIT=70000     # 1h，约 8 年
LQ_CRYPTO_SYNC_START_MS=              # 可选起始时间（epoch ms）
LQ_CN_SYNC_DAILY_LIMIT=2000           # A股 1d，约 8 年
LQ_CN_SYNC_INTRADAY_LIMIT=800         # A股 15m，上游硬上限
```

## 各方案的可用性

| 回测需求 | 加密 | A股 |
|---|---|---|
| 单次回测（≤2 万根） | ✅ 1h 覆盖 2.3 年，1d 覆盖 5.5 年 | ✅ 1d 覆盖 8 年 |
| 参数优化（≤5,000 根） | ✅ 全部周期 | ⚠️ 只有 1d / 15m |
| Walk-forward（多窗口） | ✅ 1h 足够 | ⚠️ 建议用 1d |
| XGBoost 等 ML（需 4200+ 根暖机） | ✅ 1h / 1d | ✅ 仅 1d |
| 跨市场组合分析 | ✅ | ✅（用 1d） |

**A 股结论**：长期研究用 **1d**（8 年）；分钟级只能用最近 77 天，适合验证
执行细节而非统计显著性。
