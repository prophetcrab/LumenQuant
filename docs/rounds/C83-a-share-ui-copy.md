# 迭代记录 C83：A 股下单界面的两处误导

## 背景

C79–C82 修的都是后端资金安全逻辑。这一轮在 2K 浏览器里实际操作 A 股下单界面，
检查这些改动的结果是否被正确呈现——发现两处文案与实际规则不符。

## 缺陷一：可用资金的说明写着 T+1

```
可用资金  ¥268,761.89
          含 T+1：当日买入次日可卖        ← 说明的是股份，不是现金
```

T+1 冻结的是**股份**，资金从来不被 T+1 限制（卖出所得才走 T+1 在途）。
把股份规则写在资金数字下面，会让用户以为自己的钱也被锁住了。

改为「可立即用于买入」；有挂单冻结时仍显示「挂单冻结 ¥X」。

## 缺陷二：按钮被禁用但不说明原因

卖出按钮在可用量为 0 时正确禁用，但界面上没有任何解释：

```
持仓 100 · 可卖 0
[卖出 贵州茅台]  ← 灰色，点不动
```

用户只看到一个失效的按钮，需要自己推断是 T+1 造成的。这类"静默禁用"
在多处都会出现（涨停不能买、超量不能卖），统一补上原因：

| 条件 | 提示 |
|---|---|
| 卖出且可卖 ≤ 0 | 当前无可卖数量：当日买入的股份需次日才能卖出（T+1）。 |
| 卖出且数量 > 可卖 | 可卖 N 股，已超出可用数量。 |
| 卖出且跌停 | 当前标的跌停，无法卖出。 |
| 买入且涨停 | 当前标的涨停，无法买入。 |

### 一个被自己写错的分支

第一版把 T+1 提示挂在 `sellBlocked` 上，而 `sellBlocked` 的含义是**跌停**
（`buyBlocked` 同理是涨停）。于是可卖为 0 时显示的是
「可卖 0 股，已超出可用数量」——技术上不算错，但不是用户需要的那句话。

改成直接判断 `available <= 0`，并把跌停单独列出。在浏览器里重新验证后：

```
可立即用于买入
持仓 100 · 可卖 0
当前无可卖数量：当日买入的股份需次日才能卖出（T+1）。
```

## 验证

- 2K 浏览器实测：买入模式下显示「可立即用于买入」；切到卖出并选中
  600519.SH 后显示完整的 T+1 解释，按钮保持禁用；
- `tsc --noEmit` 干净，66 项前端测试通过，`vite build` 通过。

## 这类缺陷为什么值得单独记一轮

它们不影响任何数值正确性，也不会有测试报错。但它们决定了用户**能否理解**
系统为什么拒绝他的操作。一个禁用的按钮没有原因说明，用户体验上等同于
"系统坏了"——而真实原因只是他不该在当天卖出刚买的股票。

前端验证不能只看"页面能打开、数据对得上"，还要看**失败路径是否可解释**。
