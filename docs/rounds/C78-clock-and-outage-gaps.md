# 迭代记录 C78：两处"用错时间基准"的缺陷

## 缺陷一：A 股 bar 的收盘判定用了加密时钟

C74 加了 `closed_only` 过滤，C77 之后它已覆盖原生序列、聚合、实时追加三条路径。
但过滤本身要回答"现在几点"，而 `MarketService._now_ms()` 取的是
`CompositeLiveProvider.clock`：

```python
@property
def clock(self):
    if self.crypto is not None:
        return self.crypto.clock      # ← 永远优先返回加密引擎
    ...
```

合成模式下加密时钟是 **60x 加速**的，A 股时钟只在交易时段推进。两个市场同时启用时，
A 股的日线会被按加密的"当前时间"判断——一个 60 倍的时钟可以在真实 15:00 之前很久
就跨过当日收盘，于是**未收盘的日线被当成已收盘**交给回测与实盘信号。

这正是 C74 想消灭的问题，从"时钟选择"这条路径又溜了回来。

### 修复

- `CompositeLiveProvider.clock_for(symbol)`：按标的所属市场返回对应时钟；
- `MarketService._now_ms(symbol)` 优先用它，`clock` 仅作为没有归属时的兜底。

### 验证

```
修复前（用加密时钟 18:00 判定 A 股 06:20）：closed_only 返回 2 根（含今日未收盘）
修复后：                                       返回 1 根（仅昨日）
A 股时钟推进到 15:01 后：                      返回 2 根
```

测试 `test_a_share_bar_is_judged_by_the_a_share_clock` 在还原修复后失败，
确认它真的覆盖了这条路径。

## 缺陷二：轮询中断后落库伪造的 bar，且漏掉整段历史

加密报价引擎按"上一个桶 → 新桶"的顺序累积 15m bar。如果轮询中断两小时再恢复，
累积器里那根 bar 的时间戳仍是中断前的桶，于是：

- 它被当作"已收盘"落库，而 high/low 只来自中断前后两个采样点；
- 中间 7 个桶完全不存在；
- 成交量是 0（ticker 无法提供单根量）。

实测复现（中断 2 小时）：

```
落库 1 根: O=80000 H=80000 L=80000 C=80000 V=0     ← 伪造
从首根到当前的桶数: 8                               ← 7 根缺失
```

原来的 `_authoritative_bars` 只取最近 3 根，覆盖不到缺口；`_persist_closed`
遇到已存在的时间戳直接跳过，所以**已经以量 0 落库的坏行永远修不好**。

### 修复

把"收盘落库"重写为一条同步路径 `_persist_closed`：

1. 每个标的在每次有 bar 收盘时拉取一次 klines（`limit` 按缺口大小计算，上限 500）；
2. 拿到的权威 K 线同时用于三件事：给收盘 bar 真实 OHLCV、补齐中断期间缺失的桶、
   修正已存的行中 `volume == 0` 的记录；
3. 跨度过大的累积 bar（超过 2 个桶）直接丢弃，不落库——只观测到缺口两端的
   高/低点不是一根真实的 bar；
4. 合并掉重复的 `_authoritative_bars` 与 `_backfill_gaps`，只保留一个写入函数
   `_write_bars`。

### 验证

同一场景，修复后：

```
落库 7 根，全部 volume > 0，high > low
第 8 个桶是当前进行中的，正确地没有落库
```

真实网络回归：6 个标的实时在线，15m 三根全部带真实成交量
（488.9 / 333.2 / 270.2），日线量 1744.14 与 klines 一致。

## 回归

后端 **470 passed**（新增 3 项），前端 66 passed，`tsc` 与构建干净。

## 已知限制

1. **补历史依赖上游可达**：中断恢复时若 klines 仍不可用，累积 bar 会先以量 0
   落库（并在下次成功同步时被修正），缺口保持到下次成功拉取。
2. **单次补历史上限 500 根**：约 5 天的 15m 数据；更长的中断需要多次或手动
   `/market/data/sync`。
3. **不做跨日缺口检测**：只处理 15m 桶，日线由桶滚动而来，因此日线的完整性
   间接依赖 15m 的完整性。

## 缺陷三：A 股侧存在完全相同的缺口问题

加密侧修完后检查 A 股，发现同一模式：`_close_finished` 只看"是否有更新的桶"，
不看这根 bar 跨了多久。轮询中断 30 分钟后恢复，累积 bar 带着中断前的时间戳被落库：

```
落库 1 根: O=1005 H=1005 L=1005 C=1005 V=0     ← 单采样伪造
应有 2 根（10:00 / 10:15）                      ← 10:15 完全缺失
```

A 股有现成的分时接口（`intraday_bars`，腾讯 m15），因此采用与加密相同的策略：

- 每次有 bar 收盘时按缺口大小拉取 15m 序列（上限 320，约 5 个交易日）；
- 权威序列同时用于给收盘 bar 真实 OHLCV、补齐缺口、修正已存 `volume == 0` 的行；
- 跨度过大的累积 bar 丢弃而非落库。

### 阈值从 2 收紧到 1

第一版把"可信跨度"设为 2 个桶，测试立刻暴露问题：中断 30 分钟正好落下
2 个桶的跨度，被误判为可信并落库。

正确的不变量是：**正常收盘时，bar 时间戳与当前桶之间恰好差 1 个桶**。
大于 1 就意味着至少有一个桶没被观测到。两个引擎统一改为 1。

### 验证

```
修复后（中断 30 分钟 + 分时接口可用）：
  t=10:00 O=1005 H=1010 L=1000 C=1008 V=300   ← 交易所值
  t=10:15 O=1008 H=1018 L=1006 C=1015 V=600   ← 补齐
修复后（分时接口不可用）：
  不落库，缺口保留，等下次成功拉取再补
```

### 一个被排除的误报

真实网络测试里看到 A 股 15m 返回 `O=H=L=C, V=0`，一度以为是伪造 bar 落库。
实际是**内存中的当前桶**：盘中首次启动只采集到一个价格，蜡烛自然是平的。
连续三次轮询确认它在正常累积（高 1318.75→1318.88→1318.93，量 31→76→105），
且数据库中 `15m` 行数为 0——当前桶不落库这条契约是成立的。
