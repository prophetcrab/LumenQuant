# 迭代记录 C88：日线完整性与两条重建路径的差异（验证，非修复）

## 背景

C87 让 `prev_close` 取上一交易日的日线收盘。这条修复的正确性依赖一个前提：
**日线序列本身是完整的**。这轮做的就是验证这个前提，以及两条数据路径
（合成 vs 实时）在日线口径上是否一致。

## 一、合成模式：日线与 15m 完全一致

seed 后推进若干 tick，逐日核对日线与当日 16 根 15m 的聚合：

| 日期 | 15m 根数 | O/H/L/C/量 是否一致 |
|---|---|---|
| 2026-10-22 | 16 | 全部一致 |
| 2026-10-21 | 16 | 全部一致 |

合成引擎的日线由 15m 收盘滚动而来（`upsert_daily_bars`），因此两者必然一致。
这也是 C87 能安全依赖日线收盘的前提。

## 二、实时模式：日线取交易所值，15m 是采样重建

用腾讯真实数据跑一轮后核对：

```
600036.SH  daily H=42.30  |  15m agg H=42.19   ← 不一致
600519.SH  daily H=1322.00 |  15m agg H=1321.88 ← 不一致
601318.SH  daily H=51.30   |  15m agg H=51.30   ← 一致
688981.SH  daily H=101.00  |  15m agg H=101.00  ← 一致
```

收盘价全部一致，**高点偶有差异**（0.01–0.11）。

### 这是预期行为，不是缺陷

- **日线**由报价直接写入（`_sync_today_daily`）：报价给出的是交易所当日
  真实的 O/H/L，包含所有成交；
- **15m** 由 15 秒轮询的价格路径重建：只反映被采样到的价格，两个采样点
  之间的瞬时高点若未被采到，就会丢失。

因此日线更准确，15m 是近似。`docs/delivery/realtime-data.md` 的「已知限制」
已写明这一点："15m 线是重建的……真实极值可能被漏掉"。

### 采样精度决定差异大小

差异出现在波动快、极值短促的标的上（600036 高点差 0.11、600519 差 0.12），
在波动平缓的标的上完全不出现（601318、688981）。这与"采样漏检"的机制一致。

若需要 15m 也精确，唯一办法是缩短轮询间隔或改用上游的分时接口按桶拉取——
代价是请求量和限流风险，且对 A 股 15 分钟级的策略意义有限。

## 三、当日日线的 15m 覆盖数

实时模式下，当日日线存在但 15m 只累积了 11 根（截至盘中某时刻），这是因为：

- 15m 从进程启动后才开始累积；
- 日线由报价直写，包含启动前的全部成交。

两者覆盖范围本就不同，**日线量与 15m 量和也不相等**（614,446 vs 613,603），
差额正是进程启动前的成交——这正是 C74 选择"日线直写报价"而非"由 15m 求和"
的原因。若由 15m 求和，日线量会永久少掉启动前的那部分。

## 结论

本轮没有发现需要修复的缺陷。验证确认：

1. 合成模式的日线可安全作为 C87 的 `prev_close` 来源；
2. 实时模式的日线是交易所权威值，比 15m 更准；
3. 两个模式各自的自洽性成立，跨模式的行为差异有明确文档说明。

## 回归

后端 **493 passed**（本轮无新增测试，也未改动代码）。

## 留给后续

若将来要把 15m 也做到与日线同等精度，可选方案：

1. 缩短轮询到 3–5 秒（成本：请求量 ×3–5）；
2. 每个 15m 桶结束时用 `intraday_bars` 覆盖该桶（腾讯 m15 接口，
   C78 的补历史已具备能力，可复用）；
3. 接受当前精度，在策略侧只用日线做长周期判断。

第 2 项成本最低，且 C78 已经实现了按桶拉取的基础设施。

## 四、把"逐桶对齐"从可选方案变成实现

上面第三节的第 2 项（每个桶结束时用 `intraday_bars` 覆盖该桶）其实**基础设施
已经存在**——C78 的补历史路径就会拉 15m 权威序列。真正缺的是一行判断：

```python
# 修复前
if stored.volume <= 0 and row["volume"] > 0:
    stored.open, stored.high = row["open"], row["high"]
    ...
```

只有"量为 0"的坏行会被修正。可是**由采样重建的 bar 也有非零成交量**
（轮询得到的累计量差分），所以它永远不会被覆盖。实测到的
`daily H=42.30 vs 15m H=42.19` 那 0.11 的差距，就这样永久留在库里。

### 修复

`_write_bars` 增加 `authoritative` 参数：

- **权威值在手** → 无条件覆盖已存行（OHLCV 全部）；
- **端点不可达** → 只填空缺，绝不把已有的精确行降级成采样值。

第二条很重要：网络抖动时若让采样值覆盖精确值，同一个桶会在"精确 → 粗糙"
之间来回跳，用户看到的高低点会随时间变化。

### 验证

| 用例 | 断言 |
|---|---|
| 采样值（非零量）被权威值替换 | high 从采样值变为交易所的 10.5，volume 700 |
| 端点故障不降级 | 已存的精确行（high 10.5、volume 700）在后续故障轮询后不变 |

第一个测试还原旧条件（`if stored.volume > 0: continue`）后失败。

还原验证第一次没有成功，原因是测试本身没让采样 bar 真正落库——
第一次 poll 时当前桶还没收盘，`volume` 也是 0。加上"同桶再采一次"
让差分产生非零量、再让桶收盘，测试才真正覆盖到这条分支。
