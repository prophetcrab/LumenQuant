# 迭代记录 C45：按标的与周期删除 K 线

## 动机

C38 的文档末尾写着："数据页仍不能删除某个标的的历史（只能覆盖）。这是下一步的自然需求。"

补齐前先确认它为什么重要：数据一旦导入错误（选错标的、误导入其他周期），
唯一的手段是"用正确的数据覆盖它"。如果那批数据本来就是多余的，
覆盖只会留下另一份多余的数据。而且 A 股日线的最后一根会反过来影响
`prev_close`（涨跌停基准），错误的序列会持续污染后续交易。

## 后端

`DELETE /api/data/series?symbol=&timeframe=`

```python
removed = DataService(session).delete_series(symbol, timeframe=timeframe)
# {"symbol": "600036.SH", "timeframe": "1d", "deleted": 812}
```

三个要点：

1. **返回删除条数**：调用方需要知道实际动了多少行，而不是一个笼统的 204。
2. **校验周期**：非法周期返回 422 并列出允许值，与导入的校验保持一致。
3. **重算 `prev_close`**：删掉日线后，如果还有更早的数据，
   把 `prev_close` 拉到剩余序列的最后一根；否则保留原值。
   这一步很关键——涨跌停是从 `prev_close` 算的，指向一根已不存在的 K 线没有任何意义。
4. **审计**：记录 `data.series_deleted`，含周期与行数。

同时失效 `coverage` 与该标的的 `quality` 缓存（复用 C38 的 `invalidate`）。

## 前端

覆盖表每行在"导出 CSV"旁加"删除"，点击弹出确认框：

> 将删除 **000001.SZ · 15m** 的 **572** 根 K 线。
>
> 此操作不可撤销。依赖该数据的回测与自动运行会因缺少历史而失败或信号不足；
> 如果要修复数据，通常应当重新导入覆盖而不是删除。

确认按钮为 `danger` 样式。删除成功后 toast 报告实际删除条数。

### 为什么提示"通常应该重新导入"

删除是更危险的选择。用户真正想要的往往是"我有更好的数据，换掉坏的"，
那是覆盖导入。把这句话放在对话框里，能拦住一部分误操作。

## 设计取舍

- **为什么用 DELETE 带 query 参数而不是 body**：DELETE 的语义是"删除这个资源"，
  资源标识放在 URL 里，`/data/series?symbol=..&timeframe=..` 本身就是资源路径。
  带 body 的 DELETE 在代理与客户端里支持不一致。
- **为什么不支持"只删某个时间段"**：那需要区间选择 UI 与更细的审计，
  而当前的痛点（整段导入错了）用整段删除就能解决。区间删除留作后续。
- **为什么不在删除前自动备份**：导出功能已经在同一行旁边，用户想留档可以一键导出。
  自动备份会在服务端留下用户没意识到的文件，反而增加混乱。
