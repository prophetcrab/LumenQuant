# 迭代记录 C36：真实数据研究链路实践

## 动机

前几轮的验证方式是"针对已知缺陷写测试"。这一轮换成**像用户一样使用系统**：
接真实数据，跑一遍完整的研究链路（同步 → 优化 → 滚动验证），看哪里不合理。

优化的价值在于它的输出会直接影响决策，所以这条链路上任何"沉默"都是危险的。

## 缺陷一：滚动验证丢窗口，且不说

真实数据 600036.SH 日线 800 根，参数空间 `fast∈{5,10,20}`、`slow∈{30,60}`，请求 4 个窗口：

```
walk-forward test window 0 failed
ValueError: not enough candles for warmup
```

响应是 200，但只有 3 个窗口，`index` 从 2 开始。

**根因**：测试窗口长度按参数空间的**第一个组合**（`slow=30`，暖机 31 根）算成 50 根。
但优化器可能在训练段选中 `slow=60`（暖机 61 根），这时 50 根的样本外区间根本暖不起来，
`BacktestEngine` 抛 `not enough candles`，代码 `except Exception: continue` 把它吞掉。

两个问题叠加：

1. **窗口尺寸按单个组合算**，应该按整个网格里最长的暖机算
2. **吞掉异常后不报告**，用户看到 3 个窗口会以为只跑了 3 个

### 修法

```python
warmup = self._max_warmup(strategy, space, base_params)   # 遍历整个网格
```

`_max_warmup` 对每个参数组合算暖机并取最大值。网格上限 500 组合，这点开销可以忽略。

同时保留 `continue`（一个窗口失败不该毁掉整次验证），但在报告末尾统计并告警。

## 缺陷二：结构性告警被覆盖，从来没显示过

修完尺寸后发现，即使窗口确实被丢弃，告警也不出现。查下去发现：

```python
report.warnings.insert(0, "数据只够完成 N 个窗口…")   # 写进去
report.warnings = self._warnings(report)              # ← 直接覆盖掉
```

`_warnings()` 返回一个新列表，赋值把前面插入的两条结构性告警**全部丢弃**。
也就是说"数据不够、已自动缩减窗口"这条消息从上线起就没到过用户眼前。

**修法**：先收集结构性告警，最后拼接：

```python
report.warnings = structural + self._warnings(report)
```

## 缺陷三：优化器对 15 个百分点的衰减保持沉默

真实数据跑参数优化：

```
样本内  +16.07%
样本外   +1.15%
warnings: []
```

样本外是正的，所以"过拟合"检查（只在 `oos < 0 < is` 时触发）不响。
但 16% 的优势在未见过的数据上只剩 1%，这就是过拟合，只不过结局没那么难看。

对比滚动验证：它的告警阈值是**平均训练→测试衰减 > 10 个百分点**。
两个工具对同一现象用了两套标准。

**修法**：优化器采用同样的阈值。

```python
DEGRADATION_WARN_PP = 10.0
if enough_oos and best.in_sample_return_pct > 0:
    degradation = best.in_sample_return_pct - best.out_of_sample_return_pct
    if degradation >= DEGRADATION_WARN_PP:
        warnings.append(f"样本内 {is_}% vs 样本外 {oos}%，衰减 {degradation} 个百分点…")
```

修完后同一次优化输出：

> 样本内 +16.07% vs 样本外 +1.15%，衰减 14.92 个百分点；最优参数在未见过的数据上大部分优势消失

## 修完后的真实数据表现

```
windows: [(1, slow=60, 71 根, +0.00%),
          (2, slow=60, 71 根, +0.00%),
          (3, slow=30, 71 根, -1.78%),
          (4, slow=60, 71 根, +0.00%)]
agg: windows_completed=4/4, skipped=0, positive_pct=0.0
warnings:
  - 仅 0% 的窗口样本外为正（0/4），策略在当前标的上不稳定
  - 平均训练→测试衰减 10.64%，训练期表现被明显高估
  - 平均每窗口仅 0.2 笔交易，统计意义不足
```

4 个窗口全部完成，每个 71 根（≥ 暖机 61 + 3）。结论也很诚实：
双均线在招商银行日线上几乎没有样本外盈利能力，且交易太少不足以判断。

## 设计取舍

- **为什么测试窗口要按最大暖机而不是平均**：窗口是被"用一次"的资源。
  只要有一个可能被选中的参数组合暖不起来，那个窗口就有概率白费。
- **为什么不直接跳过暖机过长的组合**：那是优化器该做的判断，
  滚动验证的职责是给优化器一个公平的擂台。
- **为什么保留 `except Exception: continue`**：单个窗口失败（数据缺口、极端参数）
  不该让整次验证失败；但必须让失败可见。

## 后续

- 滚动验证的样本外区间只有 71 根（约 3 个月），对日线策略偏短。
  这不是缺陷而是数据量与窗口数的权衡，报告里已经通过"交易数不足"告警表达。
- 优化器的 `robust_alternatives` 在真实数据上返回空——因为要求 `trade_count >= 5`
  且收益为正，而当前标的的交易数太少。这是正确的严格性，不是 bug。
