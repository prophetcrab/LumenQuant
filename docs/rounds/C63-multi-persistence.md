# 迭代记录 C63：多标的回测的持久化与历史

## 动机

C61/C62 加的多标的回测是**用完即弃**的：跑完看到结果，切到别的标签就没了，
想对比上周的配置只能重跑——而重跑得到的数字未必一样（行情在推进）。

单标的回测从 R05 起就会落库、有历史列表、可点击载入。多标的没有，这是明显的不一致。

## 实现

### 独立的表

```
multi_backtest_runs
  id, strategy, symbols_json, timeframe, market
  params_json, config_json, weights_json, rebalance_bars
  metrics_json, equity_json, comparison_json, components_json, warnings_json
  initial_capital, final_equity, bars, started_at, duration_ms
```

**为什么不复用 `backtest_runs` 用逗号拼 symbol**：组合分析（C31）按时间戳
对齐多条回测，它假定一行就是一个标的。塞进多标的数据会让那次对齐逻辑读到
无法解释的行。两套形状，两张表。

### 接口

```
POST   /api/backtests/multi        运行并保存，返回含 id
GET    /api/backtests/multi?limit  历史列表（摘要）
GET    /api/backtests/multi/{id}   完整结果
DELETE /api/backtests/multi/{id}
```

列表返回摘要（不含权益曲线），点击时才拉完整结果——20 条记录的权益曲线
加起来可能上兆字节，没有必要在打开页面时全部传输。

### 前端

多标的标签底部新增历史列表：时间 / 策略 / 标的 / 周期 / 收益 / 回撤 /
再平衡方式，点击载入、可删除。

载入的结果与刚跑完的结果共用同一套渲染，不区分来源——
用户看到的是"这个配置的结果"，不关心它是刚算的还是存下来的。

## 顺带修掉：耗时统计口径错误

第一版把 `duration_ms` 的计时起点放在组装阶段，得到 1.71ms——
这个数字看起来像"多标的回测只要 2 毫秒"，而实际上三次 300 根的回测
加数据读取远远不止。

改为在方法入口计时：

```
duration_ms: 40.63
```

这才是用户感知的耗时。

## 设计取舍

- **为什么失败不落库**：一次被 422 拒绝的请求没有任何可回看的信息
  （没有曲线、没有指标），存一条空记录只会污染列表。
- **为什么删除是硬删除**：这些记录是研究产物，不是账务凭证。
  需要留档可以导出，不值得为它们引入软删除与归档状态。
- **为什么列表限制 200 条**：与单标的回测一致。超出说明该清理了。
- **为什么不在载入时恢复表单**：载入只恢复**结果**，不覆盖当前的策略/标的
  选择。用户可能正在配置新的一次运行，被历史记录改掉输入会很恼人。

## 后续

- 历史列表没有分页，只有 limit。记录多了会需要游标分页。
