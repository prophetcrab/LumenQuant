# 迭代记录 C17：接入真实 A 股行情

C15 列出的第一项未验证内容：**真实行情源**。本轮落地。

## 选型

调研了几个公开数据源：

| 源 | 实时报价 | 日线 | 15 分钟线 | 结论 |
|---|---|---|---|---|
| 东方财富 `push2his` | 可用 | 连接被重置 | — | 不稳定，放弃 |
| 新浪 `hq.sinajs.cn` | 403（需 referer 白名单） | — | — | 放弃 |
| **腾讯 `qt.gtimg.cn` / `ifzq.gtimg.cn`** | ✅ | ✅ | ✅ | **采用** |
| AkShare | 依赖腾讯/东财等上游 | ✅ | ✅ | 放弃：1.3MB 依赖 + 数十个传递依赖，而底层接口本身可直连 |

选择直连腾讯的三个公开接口，不引入 AkShare。理由：

1. 依赖只有 `httpx`（项目已有）；
2. 解析逻辑可控、可测（MockTransport 即可覆盖）；
3. 出问题能直接定位到具体接口，而不是埋在库的几十层封装里。

## 架构

新增 `app/modules/cn/sources/`：

- `base.py`：`MarketDataSource` 协议、`Quote`/`BarBatch`/`SourceHealth` DTO、代码转换；
- `tencent.py`：三个接口的实现；
- `sync.py`（上级目录）：`CnDataSyncService`，负责入库、刷新昨收、记录审计。

设计要点：

- **可插拔**：`LQ_CN_DATA_SOURCE=synthetic|tencent`，默认 `synthetic`，离线可用；
- **不阻塞启动**：`LQ_CN_SYNC_ON_START=true` 时启动同步，失败只记日志、保留本地数据；
- **单标的容错**：一个代码失败不影响其余标的，错误逐条返回。

## 三个真实的解析陷阱

### 1. 日线字段顺序：收盘在最高/最低之前

腾讯返回 `[date, open, close, high, low, volume]`。按直觉写成
`[open, high, low, close]` 会静默交换列——**不报错、K 线图看起来也"像"K 线**，
但最高价可能小于收盘价。

测试 `test_daily_bars_respect_close_before_high_ordering` 专门锁定这一条。

### 2. 行情是 GBK 编码

`qt.gtimg.cn` 返回 GBK。按 UTF-8 解码会抛异常或产生乱码股票名。
实现里显式 `decode("gbk", errors="replace")`，测试用 GBK 字节构造夹具。

### 3. 合成历史与真实数据不能混

第一次真实同步后：

```
日线: [1705.46, 1680.92, 1639.21, 1695.02, 1676.20]  ← 合成
快照: 1676.20  涨幅 +26.51%   ← 完全错误
```

原因是合成行情与真实行情在同一代码下处于**完全不同价格水平**
（合成约 1695，真实约 1331），而合成时钟还可能跑在真实时间之前。

先尝试"删除早于真实首根的数据"，无效（合成数据时间戳更晚）；
最终改为**全量替换**：上游抓取成功后，删除该标的全部旧 K 线再写入。

修复后：

```
日线: [1329.00, 1324.97, 1331.88]   涨幅 +0.52%（与真实公告一致）
涨跌停: 1192.47 / 1457.47（基于真实昨收 1324.97）
```

## 真实数据验证

启动时同步 8 个 A 股标的，结果：

| 检查项 | 结果 |
|---|---|
| 数据源健康 | `available: true`，延迟 392ms |
| 滞后期 | 8/8 标的 `stale_days = 0` |
| 茅台报价 | 1331.88，昨收 1324.97（与腾讯实时一致） |
| 涨跌停区间 | ±10% 基于真实昨收 |
| 同步耗时 | 8 标的约 1.2 秒/标的 |

## 仍未验证

- 真实**实盘下单**（需券商权限，与数据源无关）；
- 腾讯接口的长期稳定性与限流策略（需持续观察，项目未实现自动退避重试）；
- 复权口径：使用前复权（`qfq`），与券商的除权处理需逐家核对。
