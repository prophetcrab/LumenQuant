# 迭代记录 C53：CSV 导入后的三段缓存

## 动机

C38 修过"导入后质量面板显示旧数据"，当时的修法是失效 `stats_cache` 里的
`coverage` 与 `quality`。但同一批数据前面还站着两个缓存，没有一起处理。

这一轮从用户操作路径反过来验证：**导入一份 CSV，然后立刻看 K 线与回测**。

## 缺陷：导入后 K 线仍是旧的

三个缓存持有同一批行数据的派生副本：

| 缓存 | TTL | 键 |
|---|---|---|
| `stats_cache` | 30s | `coverage`、`quality:{symbol}:{tf}` |
| `candle_cache` | 2s | `{symbol}:{timeframe}:{limit}` |
| `market_cache` | 1.5s | `snapshots:{market}` |

导入处理器只失效了第一个。实测：

```
import 40.x 序列 -> GET /api/market/candles -> close = 40.0
import 80.x 序列 -> GET /api/market/candles -> close = 40.0   ← 旧数据
```

窗口只有 2 秒，但足够发生这件事：用户导入 CSV → 点回测 → 回测读到旧序列。
更糟的是 1.5 秒的 snapshot 缓存：导入后 A 股页面的现价还是旧的，
而 `prev_close` 已经按新数据算好了——价格与涨跌停基准不一致。

### 修法

抽一个 `_invalidate_symbol_caches(request, symbol)`，三个缓存一起清，
导入与删除都调用它。

两处细节：

1. **`candle_cache` 用前缀**：键是 `{symbol}:{timeframe}:{limit}`，
   同一个标的不同周期/不同 limit 是不同的键，只能按 `{symbol}:` 前缀清。
2. **`market_cache` 清整个 `snapshots:` 家族**：键是 `snapshots:all` /
   `snapshots:crypto`，与标的无关。按 symbol 清是无效操作——
   我第一版就是那么写的，测试立刻证明了它没有生效。

## 顺带确认：导入后回测 0 交易不是缺陷

第一次测的时候，导入的序列是"每 7 天里 4 天涨 0.4%、3 天跌 0.3%"的平滑上行，
`sma_cross` 回测给出 0 笔交易，并附告警：

> 区间内没有产生可执行交易（策略未触发或被规则拦截）。

换成真正的周期序列（`40 + 12·sin(i/25)`）后：

```
trades: 2  ret: 175.12%  blocked: 全部为 0  warnings: []
```

确认 0 交易是策略在这个形状的数据上确实没有交叉，不是读取或撮合的问题。
告警文案也已经把这种情况说清楚了。

## 设计取舍

- **为什么不在写入时清空整个缓存**：`stats_cache` 里还有与本次写入无关的
  聚合（其他标的的 quality），全清会让并发的页面请求重新算一遍。
  精确失效成本很低，值得做对。
- **为什么缓存 TTL 不能作为"最终一致"的兜底**：1.5–2 秒在自动交易系统里
  不是"很短"。保护性止损、涨跌停判断都可能在这段时间里用到快照价格。
  TTL 是性能手段，不是正确性手段。
- **为什么不把缓存键统一成 symbol 前缀**：`snapshots` 是跨标的的批量查询，
  天然没有单一 symbol 可以归属。用家族前缀清是正确且简单的选择。

## 后续

- 这套"缓存与写入"的配对关系目前靠约定维持。可以在 `TTLCache` 上增加一个
  `invalidation_group` 概念，让写入方声明"我改了哪些组"，而不是记住前缀字符串。
  当前只有三处缓存，加抽象反而增加理解成本，先记下。
- 同步端点（`/api/cn/data/sync`）同样是写入方，最初也没有失效缓存。
  本轮一并修复：失效逻辑被提取到 `app/core/cache.py` 的
  `invalidate_symbol_caches(app_state, symbol)`，由 CSV 导入、序列删除、
  数据同步三处共用。同步只清"成功同步"的标的——失败的标的没有改动数据，
  清缓存只会让页面白白重算。
- 后台调度器（`CnDataSyncService` 的定时调用）走的是同一个端点，因此也已被覆盖。
