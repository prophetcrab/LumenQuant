# 迭代记录 C57：回测里的资金 T+1

## 动机

C56 给实盘补了 A 股卖出资金的 T+1 到账，并在文档末尾留下差异：

> 回测引擎目前仍没有"卖出资金 T+1 到账"的概念。A 股回测里同一天卖出后
> 立刻买入是允许的，而实盘会被 hold 挡住。

这一轮消除它。这是"回测与实盘一致"这条主张上最后一块已知缺口。

## 缺陷

回测引擎里 `cash` 是一个单一数字：

```python
cash = cfg.initial_capital
...
cash, trade = self._close(position, price, time, cash, reason)   # 卖出加现金
```

下一根 K 线出现买入信号时：

```python
budget = cash * cfg.position_pct        # 直接用，包括刚卖出的钱
```

而实盘里这笔钱在 `cash_holds` 里，`available_cash` 会扣掉它直到下一交易日。

**回测比账户更宽松。** 一个"A 股 T+1、当天卖出当天买入"的策略在回测里能跑出
漂亮曲线，实盘却会被拒绝——这正是最危险的那类差异。

## 修法

引入"在途资金"：

```python
settling: list[tuple[str, float]] = []     # (可释放日, 金额)
```

三处改动：

1. **每根 K 线开始时**释放到期的在途资金：
   ```python
   for release_day, amount in settling:
       if release_day <= today_key:
           cash += amount
   ```
2. **入场预算**用 `cash - 在途总额`，而不是 `cash`
3. **卖出**（信号平仓与保护性离场）把净额放进 `settling`，
   释放日 = 卖出日 + 1 天

### 为什么用"日期 +1"而不是查交易日历

回测的 K 线本身就是交易日序列。用日历日 +1 保证**下一根 K 线的日期**
一定大于释放日（周五卖出 → 周六释放，下一根是周一；节前卖出同理）。
这样不需要在引擎里引入交易所日历，也不会因为跨周末/长假而出错。

## 实测

同一个"买卖交替"的策略：

| 市场 | 结果 |
|---|---|
| A 股（T+1） | 4 笔，入场日 `3, 5, 7, 9` —— 每次平仓后隔一根 K 线才能再入场 |
| 加密（无 T+1） | 5 笔，入场日 `3, 5, 7, 9, 11` —— 末根仍能再入场 |

差异集中在最后一根：A 股策略在第 11 根有买入信号，但第 10 根卖出的资金
要到第 12 根才可用，而数据到此结束，因此那一笔没有发生。
这正是实盘的约束。

真实数据端到端复验：

```
真实数据回测  trades=7 ret=-1.91%
```

改动前是 `-1.67%`。差异来自某几次理想入场因为资金未到账而错过——
这正是实盘会发生的情况。

## 设计取舍

- **为什么在途资金不参与权益计算**：它已经是账面现金的一部分
  （`cash` 在卖出时增加，然后被移入 `settling`）。权益 = 现金 + 持仓，
  `settling` 只是"哪部分现金不能花"，不是额外资产。
- **为什么用列表而不是单个余额**：一天内可能多次平仓（不同标的在
  多标的回测里），释放日可能不同。列表保持每笔的来源清晰。
- **为什么保护性离场也走同样的路径**：止损平仓和信号平仓在资金语义上
  没有区别，都是卖出。只处理其中一种会留下同样的漏洞。
- **为什么 `cfg.t_plus_one` 同时控制股份与资金**：A 股的 T+1 是双向的
  ——股份 T+1 可卖、资金 T+1 可用。同一个开关驱动两者，
  避免出现"股份锁一天、资金立刻可用"这种不可能的组合。

## 后续

- 加密市场也没有"即时到账"之外的情形（如交易所提现延迟），
  当前模型对加密是 `t_plus_one=False`，符合现货语义。
- 融资融券、T+0 回转交易等 A 股特殊制度尚未建模，
  属于超出当前范围的功能。
