# 迭代记录 C84：集合竞价时段的日线防护（一次诚实的加固）

## 排查过程

检查跨日与盘后场景时，怀疑一个具体边界：A 股集合竞价在 09:15–09:25，
此时报价已经有一个"价格"，但当日还没有成交。`_sync_today_daily` 用
**报价时间戳**决定日线归哪天：

```python
quote_day = day_key(quote.timestamp_ms)
```

那么 10-23 09:15 的报价会不会生成一条 10-23 的日线，把当日 K 线提前钉在
集合竞价价上？

### 实测

用 09:15、`volume=0` 的报价驱动一次轮询：

```
daily rows created: 0
```

**没有生成**。原因是既有的过滤器：

```python
if quote.price > 0 and quote.volume > 0 and quote.timestamp_ms > 0
```

集合竞价阶段累计成交量为 0，这条报价被挡在门外。

## 结论：这不是一个现存缺陷

我做了还原验证——把新加的时间守卫移除，**19 个测试全部仍然通过**。
也就是说当前行为已经正确，新增的守卫不是"修复"。

按项目的验证标准，这点必须如实说明，而不是包装成发现了第五个 bug。

## 仍然做了加固，理由如下

现在的正确性依赖一条**间接**约束：`volume > 0`。这条约束的用途是"不要用
没有成交的报价写日线"，恰好也覆盖了集合竞价。但它不是为这个场景写的，
两个风险存在：

1. 上游若在集合竞价阶段返回**上一交易日的累计成交量**（非零），
   过滤器会放行，生成一条以集合竞价价开盘的伪日线；
2. 后续维护者若为了"成交量缺失时也记录价格"而放宽那个条件，
   集合竞价防线会一起失效，且没有任何测试会报错。

因此加了显式的时间判定 `_has_traded()`：

```python
def _has_traded(quote_ts_ms: int) -> bool:
    moment = datetime.fromtimestamp(quote_ts_ms / 1000, CN_TZ).time()
    return (dtime(9, 30) <= moment <= dtime(11, 30)
            or dtime(13, 0) <= moment <= dtime(15, 0))
```

两个边界都是**闭区间**，因为：

- 09:30:00 是开盘第一笔，必须算有效；
- 15:00:00 是收盘集合竞价的成交，必须算有效——否则当日日线会永久停在 14:59。

## 验证

| 用例 | 断言 |
|---|---|
| 09:20 报价（vol=0） | 不生成日线 |
| 09:35 报价（vol=500） | 生成 1 条 |
| 15:00:00 报价（收盘竞价） | 生成，收盘价与成交量都取该笔 |

后端 **488 passed**（新增 2 项）。

## 这一轮真正记录下来的东西

不是"又修了一个 bug"，而是：**一个看起来危险的边界，实测是安全的，
而它的安全来自一条不是为它写的约束。** 这类情况值得加显式断言，
但不该记成缺陷修复。

同时留给后续的一个判断依据：如果将来有人放宽 `volume > 0`，
`_has_traded()` 与这两个测试会明确挡住集合竞价场景。
